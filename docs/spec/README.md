## 条目模板

条目用 `###` 标题加字段列表的格式。`tools/quality/spec_check.py` 只解析领域文件，本 README 中的示例不会被当作真实条目。

```markdown
### ACQ-012 恢复未确认时锁定所有设备
- 规则：恢复命令或运行状态未确认时，不返回或保存当前事务数据；锁定所有设备的后台采集、对时和自动重连，重启软件前不解除。
- 来源：业务规则与变更日志_V1.0.2.md「统一冻结读取（2026-10-11）」“恢复命令或运行状态未确认时，不返回或保存当前事务数据；锁定所有设备的后台采集、对时和自动重连……”
- 状态：待确认
- 现状符合度：符合
- 冲突：D-101
- 验证：冻结待确认
- 代码锚点：par_app/protocol.py ParModbusClient.read_spectrum_transaction；par_app/coordinator.py PollingCoordinator
```

字段说明：

- **编号**：领域前缀加三位数字。领域前缀有 `ACQ` `POLL` `DLI` `EXP` `MAINT` `CONF` `UI` `MATH` 八种。编号只增不减，不得复用。
- **状态**：取值为 `待确认`、`已批准 <日期> <批准人>`、`已废止 <日期>，由 XXX-nnn 替代`。
- **验证**：取值为三种之一：测试节点 ID（测试函数上同时标注 `@pytest.mark.spec("ACQ-012")`）、内部文档 中的条目、`冻结待确认`。不能空着。
- **来源**：必须附不超过 100 字的原文摘录。没有原文的条目只算草稿。
- **现状符合度**：取值为 `符合`、`未验证`、`不符合`，括号内写依据。判定口径见下节。
- **冲突**：写关联的待裁决编号（如 `D-101（…）`）；确凿的实现缺陷写 `缺陷：<一句话>，待建 issue（DEF-nn）`，并在 内部文档 登记；都没有才写 `无`。判为 `不符合` 的条目，冲突字段不得为 `无`。

## 符合度判定口径

| 判定 | 条件 |
|---|---|
| 符合 | 有代码证据（锚点指向的实现），并且没有已知的例外路径。有测试覆盖更好，但不是必要条件。 |
| 未验证 | 缺少证据，或必须上实机、看改动前版本、看人工操作记录才能判断；原文含义不清、要等裁决才能判断的，也归这一类。 |
| 不符合 | 有反例：代码路径、复现脚本或数值推算能举出一个违反规则的具体情形。正常路径符合、只有例外路径违反的，也判不符合，括号内先写符合的部分，再写例外。 |

## 写法约定

- 「来源」字段的摘录整体用中文双引号 `“…”` 括起（`spec_check.py` 靠它识别摘录）；摘录内部原文自带的 `“”` 统一改写为 `「」`，例如 `“不再只显示「总线未连接」”`。
- 引用原文行号一律指 内部文档 的物理行号。
- 同一句原文只能有一个现行条目。发现重复时保留一条，另一条改为 `已废止 <日期>，由 XXX-nnn 替代`，不删除、不复用编号。
